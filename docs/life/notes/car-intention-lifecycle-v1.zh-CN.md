# 车辆活动全过程与出发约束

从活动意图到实际行程都要可追溯。只统计已出发车辆，会漏掉一直在泊位等待的
已选行程，无法判断改善来自交通机制还是把等待移到了评分范围之外。

`journey_audit.intention_lifecycle` 对每条已选驾车意图记录选择、登车完成、
实际出发、实际停车四个时刻。记录分为接近及登车、登车后等待出发、实际行程；
未出发意图也保留。时间裁剪到录制区间，预热与结束边界注明截断；未完成时间
只是已观察下界。缺失、重复、非有限或倒序时刻标记不一致，不当作完成。

这是一份描述性账本，未新增 success 门槛，也不改原有任务评分：

- 接近车辆和登车服务不是交通等待。
- 登车后等待未必由交通造成；原因需要另查当时的拒绝或预约事件。
- 没有选择的需求不在这份账本中；不能用它声称所有居民出行需求已满足。
- 停车事件不替代实际运动、合法泊位与身份绑定核验，更不替代 query 见证。
- 未显式记录取消时，保留未完成状态，不猜测其已取消或失败。

`scripts/engine_eval/journey_lifecycle.py` 可对原始或 gzip JSONL 离线重放，记录
解压后的输入摘要；不需要重新构建磁带。默认拒绝覆盖已有输出。

同时选择性移植 Claude `080bb16`：当首个冲突段的停止点距泊位不足一个车长加
安全间距时，先取得该段通行许可再出发，避免驶出少量距离后停在通行道路上。
未取得许可时保留真实泊位占用，不瞬移、不释放车辆、不缩短等待账本。
该条件是几何相关的通用出发规则，不是指定车辆或地图 ID 的补丁。

119 项相关检查通过，包括近泊位对向通行恢复、已有窄路/宽路/停车/改道、
运行时接线以及缺失事件、未出发、预热和结束截断。原 DP 磁带保持冻结，
不宣称这些改动已经在它上面执行过。后续应在有实际冲突的完整活动中核验，
并对比全部意图的等待、完成率、安全与开销。
