# 新行程的观测拥堵成本接入主引擎

主 `LifeEngine` 此前已有 `Reroutes.departure` 的实现与独立测试，但主循环分配步行路线时没有调用它。
缓存路线或活动路线会先照静态图分配，遇到实际停住的车、人后才触发局部避让和拥堵恢复。
这不是某个人或某辆车的特例，而是规划与当前场景状态之间的接线缺失。

现在每次分配新步行行程（包括缓存/活动证据复用）时，在方向分流之后按实际观测的静止主体足迹
检查路线。仅当原路暴露于拥堵且存在更少拥堵的合法替代路线时改选；目的地不变，主体位置不变。
没有绕行道路则保留原路线，由原运动控制器等待/避让，不创建新地面、不穿越主体、不瞬移。

这是一项软成本选择。静态道路约束、全身碰撞、支撑、实际每步运动和转移条件继续生效。
移动中的主体不当作静止障碍；将来若要考虑车辆即将启动的走廊，需要另行验证预测与让行契约。
暂不把 Claude `fb06e67` 的整套车辆前方走廊成本直接叠加进本分支。

额外规划按全场每个 tick 至多 4 次限制，发生在新行程分配时。达到预算保留原路线，仍可进入
原有受限的拥堵恢复。这个上限约束查询数，不宣称整个引擎最坏 tick 已达到实时要求。
账本分别记录方向分流与拥堵改道；计数包含搜索、改道、预算跳过和耗时。

验证覆盖：主引擎普通及缓存路径接入、绕行的实际连续执行/支撑/碰撞检查、车辆保持原位、没有绕行
道路时不虚构路线、行驶车辆不套静止成本、全场查询预算。连同行人恢复、路由、运行时、车辆、活动及
拥堵修订回归共 84 项通过。完整真实镇区回归另行绑定冻结版本；这些测试不证明七条 query 已可解。
